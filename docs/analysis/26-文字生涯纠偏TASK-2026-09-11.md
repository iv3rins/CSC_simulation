## 2. 冻结的业务不变量

| 编号 | 必须成立的行为 | 禁止的近似替代 |
|---|---|---|
| I01 | 等待选择后，step 返回，模拟线程可处理 State/Save/Load/Shutdown | `None => recv()`、等玩家才退栈 |
| I02 | 恢复 continuation 不重做已完成计划/地图/经济/伤病/结算，不重抽候选 | 月初重跑、暂停异常、旧快照叠 pending |
| I03 | 拒绝输入或效果失败，世界/RNG/decision/journal/scene/promise/pending 不产生部分提交 | 先记录成功再 apply；缺对象静默跳过 |
| I04 | 同身份同载荷重试返回同一已提交 receipt，含批次完成后和正常重启后 | 接受 200 或 409；请求端缓存当权威 |
| I05 | 同身份异载荷/异批次拒绝；并发只提交一次；旧 generation 请求不能污染载入的新运行实例 | 只比较 decisions 指纹；batch 0 重用 |
| I06 | 最终成功意味着约定持久边界已提交；仅入队则明确 accepted/202 | 收到信封即回 submitted:true |
| I07 | 相同模拟种子、合法决策与内容版本，暂停/恢复与连续执行得到相同模拟状态 | 把 request UUID/墙钟放入模拟 RNG/指纹 |
| I08 | 合法后继由已选分支+事实条件共同决定；承诺到期才回访；终态互斥规则明确 | 所有场景全局扫描只要 AfterScene 就触发 |
| I09 | 人物身份、正式赛果、合同、关系和 outcome 由真实状态支持 | 队友冒充教练；对话结束冒充又打完一场 |
| I10 | 前端只消费权威 DTO；错误/重连保留输入与可恢复状态 | 本地模拟结局；假比赛；倒计时自动代选 |

特别说明：接收确认和提交确认可采用不同 HTTP 状态，但“最终回执完全相同”“实际应用一次”“失败无半状态”的不变量不可变。正常进程重启恢复同一持久运行身份；显式载入旧档则产生新 transport generation 并隔离旧请求。具体存放位置由 T00 定稿，generation 不参与模拟确定性。

## 4. 失败处理协议：防止盲修循环

每次失败先记录：任务/输入/完整首个真实错误/预期/实际/根因假设/支持证据/最小修改点/影响面/重验命令，然后才能改。编译错误先确认接口计划；断言错误先确认行为；环境失败不要改产品逻辑。

同一个根因经过两次修复仍不通过：停止该处继续改码，状态改为 BLOCKED 或退回 RUNNING 的规划阶段，重新读文档与相邻源码、修订整体计划和当前卡片。有可验证新方案即可继续；仅在缺用户决策/外部能力时询问。禁止第三次没有新证据的补丁。

禁止为了通过而：扩大可接受状态码集合、删除/ignore 关键测试、默认选项吞错、增加无限等待、降低校验、给全模块加 lint allow、伪造数据、删旧功能、重算世界覆盖损坏存档、把“字段存在”当成“端到端接通”。

任务内运行相关子集；影响共享签名/RNG/存档时扩展对应验证，任务收尾做相应 fmt/clippy；最终跑完整门禁。已通过且无新变化不反复跑所有测试。验证是检查计划是否实现，不是用红灯随机决定下一步写什么。
