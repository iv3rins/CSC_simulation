# 22 · 生涯叙事架构审查（2026-09-10）

## 1. 结论与审查边界

保留 Rust 确定性模拟内核，围绕它补上“可暂停的职业事件 → 玩家选择 → 正式结算 → 人物记忆 → 后续场景”的闭环。现有项目已经有叙事与生涯基础，主要缺口是因果连续性和运行时协议，不是缺少几段更长的文案。

本次是面向文字生涯玩法的架构与重点代码审查，不是全仓逐行安全审计。阅读了现有分层、事件、系统、核心、服务端、存档、API 及历史审查文档；重点追踪 `csc-core`、`csc-server`、`csc-systems`、`csc-decision`、`csc-events`、`csc-entities` 的决策/推进/叙事链，抽查赛事结算与 LIVE 模型，并运行 Rust workspace 门禁。没有修改生产代码或现有测试。

基线：HEAD `cce548b`，**审查对象是当日工作树，包含用户已有的 staged/unstaged/untracked 变更**，不是裸 HEAD。仓库已有大量前端与图片删除、后端修复、文档修改；实施者不得 reset、clean、恢复旧前端或覆盖这些改动。行号为当日导航锚点，后续必须按符号重新定位。

用户目标理解：保留 CS2 职业题材，借鉴 NBA 2K 生涯故事模式的个人成长、人物关系、赛前压力、赛后反应和长期选择；不移植篮球规则，不承诺复刻某一代 NBA 2K 的具体系统。

## 3. 审查发现

P1 = 会破坏选择/恢复/结果一致性，应先修；P2 = 产品能力不足或文档/语义风险。以下“静态确认”表示源码控制流可确认；没有为本次新发现添加复现测试，实施阶段必须先补针对性回归。

### R1 · P1：批次号在通道中丢失，重复提交有跨批污染风险

- 证据：`csc-server/src/game/entry.rs:371` 检查 pending 的 batch_id 后释放锁，随后发送的仅是 `Vec<PlayerDecision>`；`game/manager.rs:137` 通道容量为 16；`game/decision.rs:223` 的接收方不重新校验批次身份。
- 触发：同一批次被快速双击/并发重试，两次请求均可能通过旧 pending 校验；第一份被消费后，第二份留在队列，被下一次 `decide` 取走。也存在校验后恰好超时并切换批次的窗口。
- 后果：下一批选择缺失或错误套用，决策日志污染。现有 `tests/api.rs:706` 的 stale 测试先等待 pending 清空，只覆盖顺序重放，不能证明并发安全。
- 修复：携带完整 batch/operation 身份的命令，在模拟状态拥有者处原子校验和消费；同 request_id 同 payload 返回原结果，异 payload 拒绝；批次身份跨恢复不可碰撞。不是把容量 16 改成 1 就算完成。
- 验收：用 barrier 控制并发/超时交错，无 sleep 运气测试；同批仅应用一次，后续批次必须等待自己的输入。

### R2 · P1：未统一校验决策全集，日志先于成功应用

- 证据：`entry.rs:371` 不验证 point/option 集合；`csc-core/src/batch.rs:104-106` 先 `DecisionRecorder::record` 再 apply；`csc-decision/src/recorder.rs:25` 会写入全部提交，找不到 point 也以 `PlayerId::NONE` 记镜像。`batch.rs:123` 找不到对应选择就跳过；部分类型未知 option 进入默认分支，转会则可能报错。
- 触发：正确 batch_id 携带空数组、漏项、重复 point、未知 point 或候选外 option。
- 后果：用户选择未完整执行却推进；或出现“记录了成功选择、部分副作用已产生、后续报错”的状态。
- 修复：共享的类型化 validator 要求 pending 与提交点集合一一对应、选项确属候选、操作者/作用对象有效；先完整验证，再原子应用与日志提交。比赛 conductor、REST、WS、CLI/自动源共用规则。Human 不得静默补默认值。
- 验收：非法输入前后世界、RNG、journal、pending 均相同；合法重试只产生一次影响。

### R3 · P1：LIVE 非法选择会消耗待决策

- 证据：`csc-server/src/live.rs:217` 的 `decide` 先 `session.pending.take()`，之后才 `request.candidates.contains(&decision)`。
- 触发：关键回合提交合法枚举但不在当下候选的选择。
- 后果：响应报错，但 pending 已清空；随后 advance 能绕过原暂停点。这是静态确认的错误路径副作用。
- 修复：先借用校验，验证成功后才取走；测试比较失败前后会话与后续可用选项。

### R4 · P1：LIVE 与职业比赛结果尚未形成单一事务

- 证据：`routes/live.rs:48-72` 接收客户端完整 `LiveMapConfig` 并交给会话 store；`live.rs:127,184,217` 只维护独立 HashMap。`routes/live.rs` 中 advance/decide/skip/watch 没有向 Engine 提交 `SeriesResult` 的路径。`csc-simulation/src/live_match.rs` 文件头也区分旧整图引擎与 LIVE 引擎。
- 后果：不能把 LIVE 中的选择解释为已经影响正式生涯成绩；刷新时重发 start 会覆盖进度（`live.rs:127` 的既有语义），`watch` 也不等价于 `Engine::mark_fixture_watched`。
- 设计裁决：首版正式比赛仍复用 conductor/settlement 的权威结果，做赛前选择和赛后文字回顾；独立 LIVE 不进入主生涯流程。逐回合干预要作为后续专项，先完成 fixture 绑定、权威阵容/seed、结果一次提交、进行中存档、重进恢复，再对玩家开放。
- 验收：进入/重连/跳过/读档后同场只结算一次，积分奖金一致；客户端不能提交 power/seed/最终比分改变世界。

### R5 · P1：阻塞式人类决策不具备持久暂停，超时会代选

- 证据：`game/types.rs:18` 为 300s；`game/decision.rs:223` 在模拟线程内 `recv_timeout`，所有类型超时统一 Auto 默认。`PendingBatch` 和 next_batch_id 仅在内存；`manager.rs:133,157` 重建时置空/置零；GameState 不保存它们。`entry.rs:195` 的 state 请求排队等待该线程；存档路由调用此方法。
- 后果：长时间读故事/断网可能错过职业选择；在待决策时请求存档会排队/超时，无法可靠保存当下悬停点。仅去掉超时会让存档/关闭等命令长期无法处理。
- 修复：把“已推进到哪里、待选什么、下一步做什么”变成可序列化执行状态，让一次 step 返回等待状态并释放线程。关键选择默认持续等待；挂机必须由用户选择策略。详细拆解见 23。
- 额外注意：超时分支还追加 WorldJournal 提示，虽然不耗 RNG，但完整 GameState 指纹包含 journal，不能声称“相同选项日志一定得到相同完整指纹”。需显式区分审计与世界语义。

### R6 · P2：目前推进节奏会跳过主角的重要时刻

- `manager.rs:205-222` 的 AdvanceSeason 无条件使用 `CareerDecisionSource`；这属于现有托管设计，不适合作为新故事模式主按钮。
- `routes/advance.rs` 只在 HTTP 接入时检查今日 LIVE 闸门；`game/decision.rs:124` 的多步循环不逐步检查下一天的叙事/比赛停止条件。不能声称 `days:30` 会在途中所有比赛日停下。
- `engine.rs:838` 普通日以日常更新为主，正式当前月赛事在跨月分支结算；新模式要定义“推进到下一重要节点”的后台步进和停点，不靠前端倒计时猜日期。
- 验收：从非比赛日推进多个日期，碰到第一场未处理的重要节点立即返回；同日期再次 continue 不重复发事件。

### R7 · P2：生活事件缺少跨场景因果与完整冷却记录

- `life_events.rs:315` 的 `_reputation` 未使用，阶段由年龄决定；不能按注释声称由年龄与声望共同驱动。
- `career.rs:244-247` 只保存最近一种事件。`life_events.rs:43,138` 只能阻止紧邻的同类重复；A→B→A 可在三月内再次出现 A。
- `life_events.rs:369` 的后果以即时声望、士气、关系变化及 LiveUpdate 为主，没有结构化未兑现承诺/追踪中的剧情弧；需要把反馈与后续触发连起来。
- `life_events.rs:402` 队友从 actor 名字反查，改名/同名不稳；接触队已有 TeamId，可复用并补队友稳定 ID。
- 修复：按类型/对象的冷却表、稳定 ActorRef、scene_instance_id、明确的延迟后果和事实前置条件；保留原数值效果，由统一 effect handler 执行。

### R8 · P2：职业记忆对重复节点去重过度

- `career.rs:266` 对所有 `CareerMemoryKind` 都只保留一条。
- 首次 Major 合理；但 TeamJoin/TeamDeparture、MVP/TOP20 若作为完整生涯回忆使用，将丢失后续换队与获奖。正式荣誉表仍存在，这不是所有荣誉数据丢失。
- 修复：首次类按 kind 去重，重复职业节点按稳定 occurrence key 去重；可由现有 journal/荣誉派生的不要再次存全量副本。旧档缺日期/对象时不得捏造，允许 legacy_unknown。

### R9 · P2：历史叙事使用当前队伍归属，回看可能漂移

- `projection.rs:45` 的比赛归属取当前 protagonist_team_id；`routes/query.rs:284` 从当前快照创建上下文，再对全部历史 journal 过滤；Narrator 同样接受当前队名。
- 换队之后，旧队比赛可能从自己的频道消失，新队入队前的比赛可能进入自己的频道；名字匹配也会放大改名问题。
- 修复：从比赛参与记录/转会时间线恢复事件发生时的主角归属，或在事件提交时存必要的 subject/participant IDs；严格区分“个人历史”与“当前队伍新闻”。不回写旧比分，不猜参与者。

### R10 · P2：文案与世界 RNG 有耦合

- `engine.rs:868,1004,1050,1083` 的日常文案选择消费 `director.rng`。现有 `Narrator::render` 则是无 RNG 的正确基础。
- 调整日常文案池或插入随机台词可能改变后续世界轨迹；同月按日推进与直接按月推进也不能未经测试就承诺世界等价。
- 修复：表现文案走固定模板或独立、版本化的派生选择；真正会改变状态的剧情随机走明确定义的持久状态/种子域。迁移世界语义时按契约 bump WORLD_SIM_VERSION，不以更新 golden 掩盖回归。
