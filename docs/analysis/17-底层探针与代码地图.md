## 一、读取协议（每份代码地图必须包含）

对每个被读取的文件，记录：
1. **文件职责**：模块文档（//!）原文 + 一句话职责判断；
2. **公开面清单**：pub struct / pub enum / pub trait / pub fn（签名 + 行号）；
3. **方法/函数地图**：每个 fn 记录——
   - 签名与行号
   - 作用（doc 注释原文或概括）
   - 被谁调用（grep 调用点，含行号）
   - 调用了谁（函数体内的关键调用）
   - 实现要点（逻辑骨架，不抄全文）
4. **疑点登记**：疑似重复 / 疑似分层违例 / 疑似死代码——只登记，结论待跨文件比对后下；
5. **判定**：每次地图完成后，回到此前"探查结论"逐条核对（证实/推翻/存疑）。

## 三、人类式维护五原则（工作法铁律，2026-09-05 由用户授予）

1. **架构先行**：先有分层/依赖的大架构（本仓库 = docs/analysis/01 分层图 + cargo 无环），一切实现、引用都从架构出发；
2. **绝不轻易造轮子**：造轮子前必查文档（docs/analysis/ 对应层）+ grep 确认无既有实现；有就复用/扩展；
3. **引用方法先看注释**：用方法先读它的 doc 注释（签名+作用+调用约定）；注释不够懂才下沉读实现——省 token、防注意力涣散；
4. **BUG 修复流程**：先定位（复现 + 缩小范围）→ 剥离分析（隔离变量/最小复现）→ 再修复 → 补测试防回归；
5. **新功能先找工具**：从文档 / GitHub 成熟案例获取工具 → 用工具实现 → 写回文档（docs/analysis 同步）→ 附充足注释。

### 探针流程对齐（把五原则落成操作）
- 读文件前：**先查 docs/analysis/ 对应层文档**（该模块已记录的 API/契约）→ 再完整读源码，对照文档找"文档滞后"点；
- 地图记录：注释优先摘录（原则 3），实现只在注释不足以回答"作用/被谁调/调谁"时才细读；
- 结论修正：地图完成后回填"此前的 grep 结论"是证实/推翻（本协议 §判定）。
