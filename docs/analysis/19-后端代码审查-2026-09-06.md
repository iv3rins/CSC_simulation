## 2. 关键数据流

### 2.1 推进（advance）

```text
HTTP/CLI/WASM
  → Engine::advance_day / advance_month / advance_season   (csc-core/engine.rs)
      → csc-time 推时钟
      → csc-tournaments 编排 + 结算比赛（规则调用 csc-simulation 纯函数）
      → csc-systems 五子引擎月度结算（化学/经济/伤病/人口/转会）
      → csc-vrs 更新排名
      → csc-events 追加 WorldJournal
      → 遇到需要人类输入 → csc-decision 产出 DecisionPoint 并挂起
```

引擎只做编排，所有"算什么"的逻辑都在 `csc-simulation` 的纯函数里——这条边界在本次审查中没有发现被突破的地方。

### 2.2 存档 / 读档

`GameState`（`csc-core/src/state.rs`）是唯一聚合根，全量可序列化：

```text
存：Engine::snapshot() → GameState → canonical JSON → CRC32 → gzip → tmp 文件 → rename 原子替换
读：文件 → CRC 校验（失败则隔离为 .corrupt）→ GameState::from_json_str
     → GameState::migrate_state()   ← 版本迁移挂载点
     → Engine::restore(state)
     → loop_::restore_locks()       ← 重建赛事锁
```

`GameState` 用 `deny_unknown_fields` + 未知版本直接拒绝，配合往返测试，是本仓库纪律性最强的一处设计。
**但迁移这一步在 `csc-wasm` 里被漏掉了（见 §5 P1-3），`restore` 的失败原子性也有问题（P1-4）。**

### 2.3 LIVE 比赛

```text
POST /games/{id}/live/start → LiveSessionStore::start(game_id, match_id)
  → 保存 LiveRoundState + round_history（逐回合击杀事件流）
  → advance / decide / skip 逐回合推进，critical_request 判定是否需要暂停
  → review 回放
```

`LiveSessionStore` 是**进程级全局**、与 `GameManager` 的生命周期完全解耦——这正是 P0-2 的根因。

### P0-2 · `LiveSessionStore` 内存泄漏 🔴

`csc-server/src/live.rs` 的 `LiveSessionStore` 内部是 `Arc<Mutex<HashMap<Key, LiveSession>>>`，
对外只暴露 `start` / `get` / `get_mut` 一类方法——**全仓库 grep 不到任何 `remove` / `clear` / `retain`**。

三条本该清理的路径全都没清：

- `DELETE /games/{id}`（`routes/lifecycle.rs::shutdown_game`）只调 `games.shutdown(id)`，不碰 `live_sessions`；
- `GameManager` 的 LRU 淘汰只处理 `games` 表，不碰 `live_sessions`；
- 比赛正常打完（`skip` 到底或最后一回合）之后，会话仍然留在表里。

**后果一（泄漏）**：每一场进入过 LIVE 的比赛都会永久驻留一份 `LiveRoundState`，其中 `round_history`
保存该场全部回合的击杀事件流。单场占用不大，但"长生涯 × 多局并存 × 进程长期运行"三者叠加下持续单调增长，
只有重启进程才会释放。而 `LiveSessionStore` 是进程级全局，连游戏局被淘汰都不能减轻它。

**后果二（功能缺陷，更容易被用户碰到）**：`start()` 在同 `match_id` 已存在时直接返回 `Err`。
因为会话永不清理，**同一场比赛一旦进入过 LIVE 就再也无法重新进入**——重连、误关页面、想重看一次，都会被拒。

> 修复建议：
> 1. 加 `LiveSessionStore::end(game_id, match_id)`，在比赛终局与 `live/skip` 走完时调用；
> 2. `shutdown_game` 与 LRU 淘汰里 `retain(|k, _| k.game_id != id)`；
> 3. `start()` 对已存在的同场会话改为覆盖重建（而非报错），使重进 LIVE 幂等。

### P1-3 · `csc-wasm` 读档跳过版本迁移 🟠

`csc-wasm/src/lib.rs` 的 `csc_restore` 直接 `GameState::from_json_str(&json)` 然后 `engine.restore(state)`，
**中间少了 `migrate_state()`**。

对比另外两个宿主，它们都迁移了：

- 服务端：`routes/lifecycle.rs` 的 `load_game` / `load_game_gzip`、`game/manager.rs` 的磁盘恢复，都调了迁移；
- CLI：`csc-app` 的 load 分支调了 `migrate`。

**后果**：v1–v4 的旧档在 WASM 单机模式下读入后，`honor_points` 仍是旧量纲（迁移里要 ×0.1），
TOP20 荣誉分因此整体错一个数量级；`version` 字段也停留在旧值，后续再存盘会写出一个"版本号说是旧版、
内容却已被新引擎改过"的混合档。这是三个宿主里唯一的不一致，属于会静默产出错数据的缺陷。

> 修复：`GameState::from_json_str(&json).map(GameState::migrate_state)`。
> 更根本的做法见 P2-6——让"parse 即完成迁移"成为唯一入口，从类型上消灭这类漏调。

### P1-4 · 读档失败会留下半恢复的引擎 🟠

`Engine::restore`（`csc-core/src/engine.rs`）是**按字段顺序逐个就地覆盖** world / vrs / tournaments /
journal / archive 的，最后一步才调 `loop_::restore_locks`。而 `restore_locks`
在 `LockRecord` 里的队伍 ID 在 `World` 中找不到时会直接 `panic!`（判定为不一致存档）。

`GameManager` 处理 `Command::Load` 时用 `catch_unwind` 捕获这个 panic 并向客户端返回 422 —— 看起来处理了，
**但 panic 发生时前面几个字段已经被新档覆盖、锁却没装上**。这个游戏局不会被销毁，
它带着"新档的世界 + 旧档的锁状态 + 缺失的锁"继续对外提供服务，后续所有查询和推进都建立在这个混合状态上。

> 修复建议（二选一，推荐前者）：
> 1. 在临时 `Engine` 上完整 restore 成功后再整体替换（构造-交换，天然全有或全无）；
> 2. 让 `restore` / `restore_locks` 返回 `Result` 而不是 panic，并在失败时回滚。
>
> 顺带一提：用 `catch_unwind` 承接可预期的"存档不一致"本身就说明错误类型建模缺了一层，
> 改成 `Result` 会同时解掉这个味道。

### P1-5 · 新增存档字段未 bump `CURRENT_VERSION` 🟠

`GameState::CURRENT_VERSION` 目前是 `8`，但结构体里已经落地了两个更新的字段：

- `scheduled_records`，字段注释自称"v8 旧存档读入时补空"；
- `sim_version`，doc 注释写的是"v9（待定，B-1）"。

两者都挂 `#[serde(default)]` 所以读旧档不报错，但版本号没动。这违反 `AGENTS.md` §0.3 的存档契约
（存档格式变化 → bump `CURRENT_VERSION` + 同步 `docs/SAVE-FORMAT.md`）。

**后果**：无法靠 `version` 区分"含 / 不含 `scheduled_records`"的存档，将来真需要为这批字段写迁移时没有锚点，
只能靠嗅探字段是否为空来猜——而"空"和"没有"在这里是不可区分的。

> 修复：bump 到 9，补 `docs/SAVE-FORMAT.md` 的版本表，并明确 v8→v9 的迁移是"无操作"（仅补默认值）。

### P2-6 · `from_json_str` 文档注释与行为不符 🟡

`csc-core/src/state.rs` 中 `from_json_str` 的 doc 注释声称会做"旧荣誉积分 → ×0.1"的量纲归一，
但函数体解析完就 `Ok(state)` 返回了；真正的归一在 `migrate_state` 里。

注释在这里不只是不准，而是**主动误导调用方以为 parse 就等于迁移完成**——P1-3 的 WASM 缺陷
很可能就是照着这条注释写出来的。

> 修复：改正注释；更好的做法是把 `from_json_str` 收为私有、只暴露一个"解析 + 迁移"的公开入口，
> 让漏调迁移在编译期就不可能发生。

### P2-8 · LIVE 关键回合的两套判定口径不一致 🟡

同一个"关键回合"概念在 `live.rs` 里有两处实现，取的比分快照不同：

- `critical_request`（实时暂停判定）用**回合开始前**的比分判断是否 MatchPoint；
- `review`（复盘回放）用事件里的 `score_a >= 12` 之类条件，那是**回合结束后**的比分，事后回贴标签。

结果是复盘标出来的关键回合集合，可能和当时实际暂停过的回合对不上——恰好在 12 分线附近
（打完这回合才到 12）的回合会被复盘标为关键，但实时并没有暂停。

> 修复：抽一个共用的判定函数，明确以"回合前比分"为唯一口径，两处都调它。

### P2-9 · debug 构建单月最多 3 次全量快照 🟡

`advance_month` 的调用路径上，`settle_month` 被调两次、`advance_month` 自身一次，
每次都有 `#[cfg(debug_assertions)] assert_no_nan(&self.snapshot())`。
`snapshot()` 是 `GameState` 的完整深拷贝（World + VRS + 全部赛事 + journal），
所以**debug 下推进一个月最多做 3 次全量深拷贝**。

这是 debug 测试耗时（本次 `csc-server` 测试套 46s）和内存峰值的主要来源之一。NaN 断言本身值得保留，
但没必要每次结算都全量扫。

> 修复建议：改为按月采样（例如每赛季首月），或只在 soak / fingerprint 测试下通过 feature 开启。

## 6. 值得保留的工程亮点

审查中确认这些设计是**真的在起作用**（有测试或门禁背书），不是文档里的口号：

- **确定性内核有真门禁**。`csc-util/src/rng.rs` 里放了 8 组与 Kotlin 原版位级对照的黄金值；
  `roll_bp` 用整数基点判定而非浮点比较，从根上消除了跨语言浮点分叉；`next_i32_bound`
  复刻上游行为的同时修正了它的负数缺陷，并配了白盒回归测试。这是整个仓库最扎实的一块。
- **存档纪律**。`deny_unknown_fields` + 未知版本显式拒绝 + 独立迁移挂载点 + 往返测试，四件套齐全。
  （P1-5 是执行时漏了 bump，不是机制缺失。）
