# 23 · CS2 文字生涯实施方案

> 状态：**拟实施设计，不是已存在 API**。依据 [22 号代码审查](22-生涯叙事架构审查-2026-09-10.md)。所有新增类型/路径需实施时先 rg 排重、校准签名，再写代码。目标是完成可运行的故事生涯首版。

## 1. 产品循环

主角是一名从弱队起步的职业选手。玩家每次打开游戏应该知道：我现在是谁、发生了什么、谁在等我回答、这个选择影响什么、接下来会发生什么。

```mermaid
flowchart LR
  A[今日处境与人物消息] --> B[训练或场景选择]
  B --> C[推进到下一个重要节点]
  C --> D[正式比赛/职业事件]
  D --> E[赛后对话与实际后果]
  E --> F[记忆/关系/承诺更新]
  F --> A
```

核心互动是阅读与抉择。赛程、数据、资金、转会是故事的事实来源；首页不再是十几个等权重指标卡。每段故事必须回答“为什么此刻找上我”，每个选择至少有一种可验证差异：即时效果、人物态度、未来可选项或延迟事件。不同选项不保证每次改变胜负，但必须改变明确的因果记录或游戏状态。

不以“训练→随机新闻→下一月”冒充剧情。不保证玩家必成传奇：失败有自己的场景、职业机会与结局。保留现有弱队 Tier4 开局，不为序章伪造 T1 合同、冠军或真实世界赛果。

## 2. 首版范围与后续范围

**首版必须完成：**可靠决策与存档、可暂停的故事推进、3 条剧情弧至少 12 个实际可达场景、简体中文、6 个页面、正式比赛事实驱动的赛前/赛后叙事、前后端联调与可复现运行说明。

**后续专项：**独立 LIVE 逐回合引擎与职业赛果的统一、复杂经纪人谈判、语音/实时 LLM、3D、更大剧情库、云部署、WASM 人类交互。这些不进入首版，不能在 UI 里显示可点击但未实现的入口。

首版比赛使用现有 `MatchConductor` 和 `SeriesSettlement` 的权威链；已有图间干预和队友失误决策若进入故事模式，必须纳入持久暂停状态。不得让旧 `LiveSessionStore` 的临时比分显示为职业赛果。正式比赛的日期如果暂时仍按月结算，界面明确显示比赛发生日与结算边界，禁止先显示模拟冠军再补算。

## 4. 先修正确性，再拆可暂停执行

### 4.1 决策提交事务

先修 22 的 R1–R3。增加共享 validation；提交只接受当前主体的完整 pending 集合。调用者传未知 point、重复 point、漏项或非法 option，返回类型化错误并保留 pending。

内部命令携带 `operation_id / batch_id / request_id / decisions`。在单局模拟线程实际消费处再次校验，不能只在 HTTP 线程预检。REST 和 WS 走同一路径；自动源的输出也经过同一校验器。

流程：

1. 读取当前运行状态与 pending，不修改。
2. 检查身份、候选全集、资源与业务前置条件。
3. 生成一个类型化效果计划，验证所有可能失败的效果。
4. 在一次状态提交中应用效果、记录 decision/journal、更新场景与版本、生成 receipt。
5. 持久保存提交结果后确认成功；重复相同 request_id 返回相同 receipt，不重复应用。

不要求每次操作克隆 20 年完整 GameState。优先“先验证全部、再执行不会失败的变更”；确实存在运行期失败时，做范围有限的事务快照/回滚或候选状态交换。未知 panic 要标记当前 operation 失败并阻止盲目续推，不能继续把半执行状态当成功局。

### 4.2 可序列化执行状态

现有 `DecisionSource::decide -> Vec` 是同步阻塞协议。不能只给它加 timeout 参数就得到可存档故事模式。

拟新增的状态语义（具体 Rust 名称可按仓库风格调整，但契约不变）：

```text
ExecutionState
  Idle
  Running { operation_id, target, phase, remaining_steps }
  AwaitingDecision { continuation, batch, scene_instance_id? }
  AwaitingAcknowledgement { continuation, scene_instance_id }
  Completed { receipt }
  Failed { operation_id, code, recovery }

Continuation
  当前月/日与阶段、尚未执行的工作
  已收集且已消耗 RNG 的待决策输入
  必要时：赛事/series/map 阶段、已完成图、当前比赛临时状态
  下一次推进的精确入口
```

约束：

- `step` 执行到下一个安全边界后返回 `Advanced / AwaitingDecision / AwaitingAcknowledgement / Completed`。返回等待后，模拟线程可继续处理查询、保存、恢复、关闭。
- 函数栈不是存档。必须在 `WorldDecisionBatch` 的 collect/apply 边界、`MatchConductor` 的决策边界显式保存 continuation；不要 catch 一个“暂停异常”然后从月初重跑。
- 同一 suspended state 恢复后不得重新生成候选、重新消耗 RNG、重复执行月度伤病/经济或已完成地图。
- 既有 Auto/CLI 可以用循环驱动相同 step API；先保证结果与现有基线一致，再逐项批准预期的模拟语义变更。
- 人类故事模式默认不以真实时间超时代选。Auto 模式保留用于压测；用户显式切换自动策略时记入配置。不要为了等待玩家增加永不释放的线程或后台任务。
- 每一个新的 stop reason 都在后台选择。HTTP 多日/多月推进也要在每个边界检查，而不是只检查开始那天。
- `advance-season` 的既有托管行为可为旧客户端保留；故事 UI 只调用新的故事 continue。故事模式不能通过旧 advance 路由绕过 pending；服务端必须统一检查模式和运行状态。

### 4.3 存档与幂等

- 当前 v9 为起点；以实施时实际 `CURRENT_VERSION` 为准递增。新增执行状态/场景进度必须 bump，并更新 SAVE-FORMAT。
- pending、continuation、下一事件/场景计数、剧情随机域状态（如果有）、内容版本、持久选择 receipt 必须进入同一存档一致性边界。
- 旧档补 `Idle` 与最小剧情进度，由已确认历史事实恢复资格，不能给旧档追加未发生的过去剧情。旧档缺失的 actor/date 保持 unknown，不能按当前队伍猜历史。
- GameState 格式版本、WORLD_SIM_VERSION、LIVE SIMULATION_VERSION、叙事 content_version、API view_version 分开说明，不用一个版本号包办所有变化。
- batch/operation 的外部身份包含恢复世代，读入旧存档后使旧网页尚未发送的命令失效。不要使用随机 wall-clock 值参与世界模拟指纹。
- 允许存档中保存已有 ID；加载时由服务端另建 transport generation，并与保存中的 pending 关联。只改变传输代号，不重算故事。
- request_id 是重试身份，不是世界随机源。receipt 保留策略必须有界；过期 key 返回明确结果未知/过期，不把旧请求当作新的副作用重放。
- 网络超时只表示确认未知，UI 先读 receipt/current state；不得自动新建 request_id 重复购买、签约或选择。

## 5. 叙事状态与内容格式

先搜索 `CareerMemory / CareerMark / season_goal / transfer_contacts / life_event_last_kind`，列出哪些字段能复用。新状态只存不能从既有事实可靠派生的内容：当前剧情弧进度、未兑现承诺、剧情专用 flags、按事件/对象的冷却、已提交场景 occurrence IDs。现有声望/关系/荣誉保持原来的事实源。

拟新增 `NarrativeDirector`：输入只读世界事实、主角进度、当前日期、刚发生的领域事件；按明确优先级选择一个场景。先处理已到期后果，再关键职业节点，再普通互动。相同候选按稳定 ID 排序；不得依赖 HashMap 顺序。

建议内容存 `assets/narrative/zh-CN/*.json`，文本复用 TextBundle 并补加载/校验；这是新的业务内容资产目录，不替代根资产源。首次加载就检查 schema、重复 ID、缺 text key、不存在的 next_scene、非法效果、无出口循环。

```json
{
  "id": "rookie.first_review",
  "content_version": 1,
  "arc": "rookie_belonging",
  "trigger": "after_first_official_series",
  "priority": "important",
  "actor_role": "captain",
  "text_key": "narrative.rookie.first_review",
  "choices": [
    {
      "id": "REQUEST_REVIEW",
      "label_key": "narrative.choice.request_review",
      "effects": [{ "kind": "create_promise", "promise": "review_before_next_match" }],
      "next_scene": "rookie.review_followup"
    },
    {
      "id": "KEEP_DISTANCE",
      "label_key": "narrative.choice.keep_distance",
      "effects": [{ "kind": "set_story_flag", "flag": "prefers_solo_preparation" }],
      "next_scene": "rookie.solo_followup"
    }
  ]
}
```

这是建议 schema，不是现有 JSON。效果用受限 Rust enum，不执行脚本字符串、eval、自由 JSON path 修改或运行期 LLM 指令。`create_promise` 必须解析成具体 actor、截止模拟节点和可检查目标，不能永远存一句话。

ActorRef 使用稳定 PlayerId/TeamId。队长等角色在触发时绑定真实人物；只有队伍关系事实存在才说“队长”。虚构经纪人等新增人物使用独立命名空间、明确标注游戏角色，不能冒充真实人物的真实言论。

## 6. 首版剧情包（3 弧 × 至少 4 场景）

| 剧情弧 | 触发事实 | 四个最低场景 | 分支差异与回收 |
|---|---|---|---|
| 新秀归属 | 新建弱队主角/首次正式系列赛 | 入队接待、首次赛后谈话、下场前兑现准备承诺、下一场后的队友反馈 | 接受团队复盘/偏向独练改变可选准备方式与下一次谈话；赢/输均有出口 |
| 压力与信任 | 首次明显失利或已存在的队友失误事件 | 失利复盘、队友私信、下一次比赛前公开/私下回应、结果后的信任回访 | 分歧可恶化也可修复；使用真实失误对象，事件不存在时不可伪造甩锅 |
| 去留与承诺 | 有真实招募接触/可签约报价 | 招募来信、留队沟通、正式报价/续约选择、转会成功或留队后的回访 | “表示兴趣”不等于签约；只有 TransferEngine 成功才写离队/加入记忆；无报价分支解释等待原因 |

每条弧至少两个可区分的终态和一个延迟反馈。用受控测试 fixture 覆盖全部分支；自然游戏抽样证明触发可达，不要求靠某一个 seed 碰运气覆盖全部剧情。

叙事正文约 120–240 汉字，2–4 段；过渡场景可短。重大场景 2–3 个选择，日常确认可 1 个。至少一个不是“收益最大/收益最小”的简单排序：例如兑现对队友的承诺会占用准备机会，选择自我表现则放弃该承诺，后续明确回应。

影响预览区分“确定影响”与“可能影响”，由后端提供，不输出虚假的 +5% 胜率。提交后显示真实结果 receipt 和未来追踪项。信息可以有悬念，前置条件和已发生结果不能撒谎。

内容节奏：同一时刻一个需要处理的主场景；非关键世界新闻不弹窗；同日最多一个普通主场景，强制职业节点可额外出现并说明原因。日常无事时允许蒙太奇跳到下一节点，不要求连续点击 30 次“下一天”。

## 7. 拟新增 API 契约

下列路径**目前不存在**，必须先写 Rust DTO、路由测试与 FRONTEND-API，前端才能对接。保留原 `/view` 与 journal 双频道；新 API 只提供故事所需的小投影。

| 方法/路径 | 输入 | 输出与语义 |
|---|---|---|
| `GET /games/{id}/career` | 无 | CareerView：当前章节/场景、可用操作、pending、revision、transport_generation、已发生事实摘要 |
| `POST /games/{id}/career/continue` | request_id、expected_revision、generation | 推进到 next meaningful checkpoint；响应当前 view/receipt，或 202 + 可查询 operation_id |
| `POST /games/{id}/career/choices` | request_id、generation、expected_revision、scene_instance_id、batch_id、完整 decisions | 统一验证/原子提交；返回 receipt，包含真实即时影响与延迟追踪 |
| `GET /games/{id}/career/operations/{operation_id}` | 无 | pending/running/completed/failed + receipt；用于超时对账 |
| `GET /games/{id}/career/history?cursor=...` | 服务端 opaque cursor | 已经历场景/选择/后果分页，不泄露未解锁分支 |

可复用旧 `/decisions` 实现 transport adapter；不能两套路由分别应用效果。无选择的场景通过 continue 确认，重复确认不得重播奖励。

CareerView 参考结构：

```json
{
  "view_version": 1,
  "revision": 18,
  "transport_generation": "opaque-server-value",
  "phase": "awaiting_choice",
  "chapter": { "id": "rookie_belonging", "title": "轮到你证明自己" },
  "scene": {
    "instance_id": "scene-12",
    "date": "2026-02-01",
    "title": "训练室的灯还亮着",
    "paragraphs": ["这里由后端提供完整的情境叙述。"],
    "actors": [],
    "choices": [],
    "fact_refs": []
  },
  "pending": { "batch_id": 7, "points": [] },
  "available_actions": [{ "id": "continue", "enabled": false, "reason": "请先完成当前对话" }]
}
```

示例空数组仅表达结构，实际待选场景必须返回可操作候选。日期来自 SimClock；按钮可用性由后端给出。UI 不根据字符串/月份猜测能否转会、训练、推进。

错误码建议：400 结构错误、404 不存在、409 版本/批次冲突、422 候选/业务前置条件拒绝、429 容量/背压；body 保留兼容 `error` 并增加 `code/retryable/current_revision`。旧实现可能把所有提交错误映成 409，不应沿用误写的“已有 429”。

WS 可新增 `career_changed {revision}` 失效通知，然后按需拉取小视图；不广播完整存档。重连流程：获取当前 revision/pending → 从各频道已确认 seq 补拉 → 对齐 UI；服务端 `next_seq` 是排他下一游标，旧 since 语义为 `seq > since`，下次 since 使用 `next_seq-1`。

当前 REST journal 带 narration，WS journal 主要带 projection；新前端不得自行猜文案。可以先将 WS 用作失效信号，以 REST 为文案权威，并用 seq 去重；如统一 DTO，要测试两种通路一致。

M2 涉及较多流程，但要按世界批次→比赛决策→adapter 顺序小步迁移；任何中间版本都保持编译，不并行重写相同文件。多智能体仅在工具实际提供且资源可用时启用，遵守当前真实并发上限；否则按 AGENTS §10 独跑，不能捏造 pro/flash 已执行或无限重试不可用模型。

## 9. 验收矩阵

| 类别 | 必须验证的行为 |
|---|---|
| 非法输入 | 空/缺/重复/未知点、候选外 option 均无副作用；pending 保留 |
| 并发与重试 | 双击、同 ID 异 payload、响应丢失后重试、旧页面跨恢复提交；世界只变化一次 |
| 暂停恢复 | 等待场景/比赛干预期间保存，重启后候选/人物/比分/RNG 连续；查询与关闭不被等待阻塞 |
| 确定性 | 同版本/资产/种子/玩法命令序列结果相同；阅读速度、重连、重复 GET、纯文案修改不改变比赛世界 |
| 事务 | 应用失败时 revision、世界、journal 与选择 receipt 保持一致；恢复不重复奖金/训练/转会 |
| 内容 | 12 场景可达、至少两种弧终态、延期回访、失败出口、无自相矛盾冠军叙事 |
| 记忆/身份 | A→B→A 冷却；重复转会保留不同事件；改名/同名演员；转会后历史叙事归属正确 |
| 推进 | 从非比赛日连续推进在中途关键节点停下；没有“需要点 30 次才进入剧情”的死循环 |
| 前端 | 初次创建→阅读→选择→结果→继续→比赛→赛后→存档→刷新恢复；错批次给可恢复提示 |
| 视觉 | 1440×900、1920×1080、768×1024、390×844；200% 字号/缩放；键盘全程可操作；无横向溢出 |

后端门禁（从 `backend/`）：

```sh
cargo test --workspace --locked
cargo clippy --workspace --all-targets --locked -- -D warnings
cargo fmt --all -- --check
cargo build -p csc-wasm --target wasm32-unknown-unknown --locked
```

先跑每个改动对应的 crate/测试，再跑全门禁一次。时间允许的最终验收补已有 release twenty_year 与 `scripts/smoke.mjs`；测试前阅读脚本的建局/删局行为，用隔离数据目录与端口。不能把 604 当未来必须恰好相等的数量，增加有效测试后总数应变化。

前端建立并记录 `typecheck / test / build / test:e2e` 脚本，安装后提交 lockfile。E2E 使用真实后端；测试 fixture 仅用于确定性分支覆盖，正式产品不得默默回退 mock。接口未就绪时显示明确错误或尚未启用状态。

启动后端的既有形式：从 `backend/` 执行 `cargo run -p csc-server -- ../assets 8080`。实施者先核对配置/持久化目录，使用空闲本地端口，不停止用户其他任务。前端 dev proxy 同源连接 REST/WS。完成后写清服务 PID、地址、数据目录、启动/停止命令，不承诺机器退出后服务继续存在。
