## 4. 关键发现

### R01 · P1：无限等待被当成持久暂停，违反 23 §4.2

**定位：** `csc-server/src/game/decision.rs:306` 的 `None => recv()`；`game/manager.rs:160` 的单局线程；`csc-core/src/engine.rs:224` 的 `advance_unit`。

故事模式只是取消超时，`DecisionSource::decide` 仍不返回；`advance_unit` 仍转调整日/整月旧调用栈。模拟线程进不了 `Command::State/Load/Shutdown` 分支。`routes/lifecycle.rs:208` 的下载保存最终仍调用 `entry.state()`，不是读取那份打补丁的共享快照。因此“打了 Awaiting 标记就能待决策保存”在当前链路中不成立。

**影响：** 玩家等待时命令排队/超时；关闭也不能及时处理。这不仅是缺几个 REST 路由，执行模型本身选错了。

**裁决：** step 到安全边界返回一个可序列化 continuation，释放模拟线程；持久化的是实际暂停状态。旧同步接口只能成为相同 step 的自动驱动适配器。禁止继续用无限 recv、暂停异常或月初回放完成 M2。对应 T02–T04。

### R02 · P1：暂停快照不代表实际执行位置，恢复路线偏移

**定位：** `csc-core/src/state.rs:31`；`game/decision.rs:227,278`；`game/decision.rs:185`；`game/manager.rs:139,168`。

ExecutionState 注释明确选择“步前状态 + 重放当前步”。`stamp_awaiting` 只覆盖共享快照的 execution；world、RNG、journal 等没有一起变成暂停点的状态。共享快照在一次推进整体收尾时刷新，多步推进内不保证是当前步起点。每个 pending 又都硬写 `remaining_steps=1`、`StepKind::Month`，已回答批次 `armed_decisions` 恒为空。source 启动从 batch 0 开始，没有从执行状态恢复 pending 的接线。

**影响：** 新字段可以序列化，但无法据此恢复“当前图/当前阶段/已用 RNG/已答选择”。继续按暂停日志第 5 项“恢复重放”实施，会把错误架构固定下来。

**裁决：** 移除或迁移这个错误语义，不只是补几处赋值。先盘点真实可暂停点及跨边界活变量，再确定值类型。v10 草稿已经出现在工作树中，不能直接降版本或假设无人保存；T00 明确草稿兼容策略，T04 实施。对应 T00、T02–T04。

### R03 · P1：成功确认早于应用，且业务失败仍可能留下成功记录

**定位：** `game/decision.rs:317,347`；`game/entry.rs:428`；`csc-core/src/batch.rs:111`；`csc-tournaments/src/conductor.rs:897`。

source 校验完成便 `reply.send(Ok(()))`，此时仅收到选择，还没返回给引擎应用。请求端随后记缓存并返回 `{submitted:true}`。`WorldDecisionBatch` 后续仍先 `DecisionRecorder::record`、再执行可能返回错误的 `TransferEngine::execute_choices`。比赛 conductor 的通用 `decide` 仍直接记录，没有调用新的共享 validator。

**影响：** 接收成功被包装成已消费的权威结果；应用/存储失败时前端已经收到成功。形状校验无法替代资源、主体、合同与效果前置校验。比赛路径与世界路径也未统一。

**裁决：** 分清 `accepted` 与 `committed`。先全部验证并形成效果计划，再一次提交世界、RNG、日志、进度和 receipt；达到约定持久边界后才确认 committed。异步接口先回 202 operation，不能用 200 冒充最终提交。对应 T02、T03、T05。

### R04 · P1：幂等语义缺失，且路由直接同步等待

**定位：** `game/entry.rs:379`；`game/types.rs:96,127`；`game/manager.rs:142`；`routes/decision.rs:34`。

1. submit 先检查 advancing/current batch，再查 receipt。已完成批次的成功重试通常在查缓存前被 409 拦截，无法返回原结果。
2. 缓存按 request ID 查后只比对 decisions 指纹，未把存下的 batch ID 纳入同一身份检查；没有 operation/generation 范围。
3. 状态拥有者收到信封后忽略 `request_id`，请求线程收到回复才插入缓存。同 ID 并发提交没有在权威线程内合并为一次事务。
4. 缓存不入存档，无实际 outcome，64 条淘汰后把 ID 当新请求。重启和旧存档载入没有完整身份隔离。
5. async HTTP handler 直接调用包含 `recv_timeout(10s)` 的同步函数，会阻塞 Tokio worker；错误又一律映射成 409，丢失满队列/服务退出等区别。

**裁决：** 单一状态拥有者处理完整身份、去重、提交和回执；已提交回执查询先于“仍有 pending”的新请求校验。必须定义重启恢复与显式回滚读档各自的 generation 语义，回执有界但过期必须明确拒绝，不能复活。等待采用 async operation 或既有受控 blocking adapter。对应 T04、T05。

### R05 · P1：测试把错误结果纳入允许范围

**定位：** `csc-server/tests/api.rs:821,878`；`game/decision.rs:475` 附近的新增 source 回归。

名为 `request_id_idempotency_same_payload_ok_diff_payload_rejected` 的测试，允许相同请求返回 `OK || CONFLICT`。注释写“不重复应用/日志不增加”，代码没有因此断言提交前后的日志/世界计数。source 测试主要覆盖“旧 batch/坏 option 后再提交合法项”，使用短 sleep 协调，不等于两个同时有效提交的受控竞态测试。

**影响：** 测试数从 604 到 633，但关键需求能在错误实现下通过。继续以全绿作为完成标准会固化偏移。

**裁决：** 验收先冻结为行为契约，历史回执重试必须相等，拒绝后状态哈希不变，重复成功只产生一条记录。用 barrier/channel 明确同步，不能放宽断言、删测或调超时绕过。对应 T01、T05。

### R06 · P1：剧情有静态箭头，没有运行时路径约束

**定位：** `narrative/content.rs:118`、`director.rs:35,114`、`apply.rs:153`；真实资产 rookie/pressure/transfer 场景。

`next_scene` 只被 schema 保存和校验，运行时没有读取并保存所选后继；导演从所有满足泛化 trigger 的场景中选取。`PromiseDue` 只查 Pending，不比较 `due_month_index`。terminal_states 不参与选择器排除。因此走团队分支也能进入 solo 回访，选择暂时不走的转会谈话仍可能进入。

具体内容问题：`pressure.trust_followup` 的前置只有完成 `pressure.before_next`，文案却说“你们打完了承诺里的下一场”；中间不要求新正式比赛。`rookie.review_followup` 说“下一场正式比赛就在明天”，也没有日程证据。当前设计让“对话点击完成”替代了比赛间隔。

**裁决：** 保存选择导致的合法后继/分支及原因，场景可达性同时受路径和真实条件约束。承诺按对应模拟日期或明确比赛里程碑判定，到期排序兑现注释。终态可有显式尾声边，但不能无条件继续互斥分支。对应 T06、T08、T09。

### R07 · P1：人物身份与比赛事实被简化成了会误导叙事的代理值

**定位：** `csc-core/src/engine.rs:236,282`。

`narrative_facts` 用“主角当前战队 ID”过滤整个 journal 的历史比赛；转会后，旧队真实参赛经历消失，新队在主角加入前的比赛反而可能算到主角身上。当前事实结构没有稳定的被引用 series/fixture 和主角参赛关系。

`begin_scene` 把 captain、teammate、coach 全部绑定为 roster 中第一个非主角的人。稳定 PlayerId 只能防 ID 漂移，不能把普通队友变成教练。角色没模型时应明确使用未具名教练/经纪人叙述，并关闭需要真实关系对象的效果。

**裁决：** 由权威结算/生涯记录提供带身份与时间的事实；用真实角色能力选择演员；保存场景事实与演员绑定，刷新不能重新选人。不要额外建立一套互相矛盾的比赛计数真相。对应 T07。

### R08 · P1：效果处理不是原子事务，文本也不总等于实际后果

**定位：** `narrative/apply.rs:24,46,72,97,104,141`；`engine.rs:316`。

- `apply_choice` 顺序直接改 world/progress，找不到对象或承诺就跳过；末尾仍消耗 active scene，返回值没有失败结果。与 Engine 注释“原子应用”矛盾。
- CreatePromise 把 `impact_certain` 直接作为实际 outcome，不验证其中承诺的所有关系/状态变化是否发生。
- 凝聚力先直接加 delta；如同一选项也有关系效果，末尾重新从 chemistry 计算 cohesion，会覆盖先前直接增量，却仍报告增量。
- AcceptTransfer 只有一条“表达意愿”的输出，没有持久意图，也没有真实签约。schema 注释却写“尝试完成真实转会”。后续不能靠这个效果写签约成功。
- StayTeam 使用 TeamJoin 记忆类型记录留队，且既有 remember 按 kind 去重，可能既污染语义又不产生所声称的新记忆。

**裁决：** 纯计划/校验 → 既有系统 handler 执行 → 由 AppliedOutcome 渲染后果；资源/演员失效时保留待选或进入明确替代分支。迁移重复的规则，禁止为 narrative 保留第二套化学/转会规则。对应 T07、T05。

### R09 · P2：加载校验器声称“完整校验”，实际只覆盖很小一部分

**定位：** `narrative/content.rs:160,169`。

目前检查重复 scene ID、空 choices、next_scene 存在与 scene.arc 存在。没有验证重复 choice/arc ID、AfterScene/DelayMonths 引用、无出口循环、效果前置、承诺引用和可达性。探针确认重复 option、自循环和 ghost after_scene 均通过。

**裁决：** 静态 schema/图校验与动态可达性场景测试分工明确；静态不能证明的世界条件用固定 fixtures 验证。错误定位包含 scene/choice/key，不能资产坏了静默当空剧情继续。对应 T06、T09。

### R10 · P2：完成标记、文档和实际代码不一致

**定位：** `PROGRESS-文字生涯-暂停点.md` 的 M1 ✅ 与 M2 已落地；`SAVE-FORMAT.md:20`；`csc-core/src/state.rs` CURRENT_VERSION。

M1 只能认定“部分改善”，不能认定“可靠提交完成”。M2 有纯值结构但暂停执行未成立；M3 内容只有原型。代码 v10，存档说明仍 v9；新 API 与 narrative 类型未完成分析文档同步；资产 13 场景写成 14。本次最新验证也不是四项全绿。

**裁决：** 以本报告覆盖完成判断，保留原进度日志作为历史记录。不要单独把文档改成“v10 已完成”来掩盖未实现的恢复契约。TASK 验收后逐项同步。对应 T00、T04、T12。

## 6. 为什么反复修：这次要约束什么

问题不在于“验证后不能修复”；发现失败并修复是正常工程过程。问题在于实现前没有锁定状态所有权、恢复边界、提交语义与验收证据，随后用局部补丁和宽松测试替代设计。

上一版 prompt 把 M0–M5 的目标讲清楚了，但任务跨度仍然太大，没有把“禁止月初重放”“必须真实回执”等约束变成先决闸门，给了模型用近似实现宣布完成的空间。本次补上：**先整体计划 → 冻结不变量与反例 → 按依赖顺序只做一个 TASK → 用固定证据验收 → 才进入下一 TASK**。

全局计划必须完成后才写生产代码；每任务开工前列文件和复用清单；失败先给根因与影响面；同一问题两次无效修复就退回计划，不进行第三次盲补丁。验收失败只允许修当前任务，不允许趁机扩展前端或其他剧情。
