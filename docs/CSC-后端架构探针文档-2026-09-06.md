## 二、核心架构事实（修复时不可破坏的契约）

1. **确定性内核**：引擎唯一随机源 `Xoshiro256StarStar`（csc-util），同种子+同决策序列=同世界。
   有 8 组与 Kotlin 位级对照的黄金值测试 + 整数基点判定（roll_bp）。**任何改动不得引入
   不确定/浮点分支到决策路径**。
2. **存档纪律**（docs/SAVE-FORMAT.md）：
   - `GameState`（csc-core/src/state.rs L57）是唯一聚合根，`deny_unknown_fields` + 未知版本拒绝；
   - `CURRENT_VERSION = 8`（state.rs L121）；迁移在 `migrate_state()`（L148）；
   - **v1–v8 版本表 + bump 规则见 docs/SAVE-FORMAT.md §2/§3**——改存档字段必须 bump + 同步该文档；
   - 已有**两个字段落地但版本没 bump**（见下方 P1-5）。
3. **读档原子性**：`Engine::restore`（csc-core/src/engine.rs L461）逐个字段就地覆盖，最后
   `loop_::restore_locks`（loop_.rs L163）——**该函数对不一致存档会 panic**（loop_.rs L168），
   且 panic 时前面字段已被覆盖（见 P1-4）。
4. **LIVE 会话**：`LiveSessionStore`（csc-server/src/live.rs L117）= 进程级全局
   `Arc<Mutex<HashMap<LiveSessionKey, LiveSession>>>`，生命周期与 GameManager 解耦（见 P0-2）。
5. **规则层纯函数**：所有"算什么"在 csc-simulation；csc-core/csc-tournaments/csc-systems 只编排。
   **新增计算逻辑应进规则层纯函数，不塞进编排层。**
6. **文件红线**（用户铁律，docs/analysis/18）：一个文件生产代码 >500 行 = 待拆分。
   当前超 500 行的文件清单见 docs/analysis/18-文件拆分作战清单.md。

## 五、模块化改造建议（"更稳健、更模块化"的落点，按需选做）

1. **大文件拆分**（收益最直接）：按 docs/analysis/18-文件拆分作战清单.md 的优先级表，
   每批拆一个 >500 行文件到 ≤500（生产代码）。铁律：零行为变化、只挪代码+改可见性、
   拆完跑 cargo check + 相关测试、测试随模块走。
2. **迁移入口收敛**（与 P1-3 合并）：`GameState::from_json_str` 收私有，只暴露
   "parse + migrate" 公共入口，杜绝第三处宿主再漏调迁移。
3. **review 数据外置**（可选，P0-2 的延伸）：若 review 需要打完即删会话，把已结束比赛的
   review 数据与活跃会话分离存储，使会话可安全回收、review 仍可用。
4. **catch_unwind 清剿**（P1-4 延伸）：grep `catch_unwind`，凡承接"可预期业务错误"的一律
   改 Result，panic 只留给真 bug。
5. **错误类型建模**：SimError 已是全仓统一错误（csc-util），新代码一律 Result<_, SimError>，
   不新增 String 错误、不 panic。
