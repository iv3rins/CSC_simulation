## 1. 测试铁律（任何情况下不违反）

1. **拟人化驱动**：不得直接改后端数据、不得用 curl/脚本直连后端写状态、不得直接改存档文件
   来伪造测试通过。**一切通过浏览器扩展（Chrome DevTools MCP）+ 前端 UI 完成**。
2. **不跳路径**：不得直接用 `navigate` 跳到某个深链接。必须从起始页开始，**跟着 UI 的引导、
   按钮、链接一步步走**（点「创建游戏」→ 填表单 → 提交 → 看结果 → 继续）。URL 变化是 UI
   行为的**结果**，不是跳转的手段。
3. **图片理解**：每一步操作后必须 `take_screenshot` 并结合页面快照（a11y tree）核验视觉，
   确认 UI 无错乱、无元素缩挤在一角、无大面积空白、无元素重叠遮挡。发现视觉问题即记为缺陷。
4. **不破坏可复现性**：测试中创建的游戏用固定 seed（默认 42）与固定选手名，便于复现。
5. **修复要走正路**：出现问题时，根据**游戏玩法**与**现有架构**做高质量修复——优先扩展既有
   的 `DecisionPoint`/`LiveMatchState`/`DecisionRecorder`/`WorldJournal`/`DecisionSource`
   体系，不重复造轮子、不引入第二个随机源、不破坏确定性核心。修复必须带单测/类型检查。
6. **零交互**：整个流程自主完成，不得要求人工输入。若遇到需要人工判断的点，按合理默认值
   继续并记录假设。

## 2. 环境自检与启动（第一步）

先执行环境自检，确保可测。**不要跳过**。

1. 确认后端可启动：
   - 项目根在 `backend/`，运行 `cargo run -p csc-server -- ../assets 8080`（后台起服务，
     等它就绪）。
   - 若 8080 被占，用 `cargo run -p csc-server -- ../assets 8081` 并记下端口，后续前端代理
     需对应。
   - 健康检查：`GET http://127.0.0.1:8080/games` 应返回 JSON（200），说明服务端在线。
2. 确认前端可启动：
   - 项目根在 `frontend/`，若 `node_modules` 缺失先 `npm install`，然后 `npm run dev`。
   - 确认 Vite 开发服务器（默认 `http://127.0.0.1:5174`，后端代理同源指向 8080）。
3. 打开浏览器（Chrome DevTools MCP / extension），访问 `http://127.0.0.1:5174/`。
   - **截图 + 快照**初始页，确认：
     - 侧边栏 15 个导航项齐全（生涯中心/我的赛程/训练中心/我的队伍/球员办公室/转会市场/
       HLTV TOP 20/世界风云/生涯日志/个人数据/荣誉与生涯/设置存档）。
     - 无 gameId（未创建选手）时落在「开局向导」或主页，符合策划：无存档首进应进入引导。
   - 若测试点 `P0-B`（开局向导）是待实现项，先记为此类，但**仍尝试走完整创建流程**。
4. 记录初始环境快照（含浏览器控制台有无报错）。控制台报错 = 致命缺陷之一。

## 3. 测试用例清单（按序执行；每项含"通过标准"）

> 每个用例：①描述操作路径（跟随 UI 一步步）②操作 ③截图核验 ④断言/通过标准。

### TC-1 开局创建选手（拟人化主流程）
- 从起始页开始。若在主页，点「去设置新建一局」/ 引导按钮进入创建（**跟随引导，不跳转**）。
- 在「设置存档」/开局向导页：
  1. 填选手 ID（如 `TesterOne`）。
  2. 选角色定位（如 RIFLER）。
  3. 选赛季目标（如 IMPROVE_RATING）。
  4. （若策划已实现）选起点队伍。
  5. 点「开始职业生涯」。
- **通过标准**：创建成功；URL 回到主页/生涯中心；主页出现该选手姓名、队伍、rating、资金；
  侧边栏「未创建选手」消失。截图核验布局。

### TC-2 训练中心（主动训练）
- 从主页点「训练中心」（**跟随**）。
- 查看 7 个训练选项（瞄准/道具/残局/体能/心理/沟通/休整）。
- 选一个专项训练排定，再选「休整恢复」。
- **通过标准**：训练页显示选项、当前已排定计划；排定后有提示；无布局错乱。

### TC-3 推进时间 → 首场比赛（世界推进）
- 使用顶部/主页的「推进时间 / 播放」控件推进到月末/赛季边界（跟随 UI，不用跳转）。
- **通过标准**：时间推进后，主页「最近战绩」出现至少 1 场记录（W/L、比分、赛事）；
  「生涯动态」出现事件；赛程页/生涯中心能追踪下一场比赛；期间无崩溃、无控制台报错。

### TC-4 比赛与 LIVE（若触发 Major/顶级赛事）
- 当玩家参与顶级赛事（Major/SuperElite/Elite）时进入 LIVE/比赛中心。
- **通过标准**：能看到逐图比分、比分条、击杀可视化、KDA/Rating 表；若是 LIVE 有决策弹窗
  （场内干预/关键回合取舍）；决策后立即有即时反馈文本；低级别赛事**不弹**现场决策。

### TC-5 球员办公室（开放自由度：换队/BP/发言/训练）
- 从主页点「球员办公室」。
- 逐项操作：设置 Major/顶级 BP、公开发言、主动训练；合同到期/买断后可看自由转会候选。
- **通过标准**：各操作卡正常、有后果提示、无空状态崩溃、无布局错乱。

### TC-6 转会市场
- 从主页点「转会市场」。
- **通过标准**：能查看转会候选、队伍信息、实力增减；空状态有下一步指引文案；无崩溃。

### TC-7 赛事世界 / 世界风云
- 打开「世界风云」与「HLTV TOP 20」。
- **通过标准**：世界新闻可读、有队伍排名/动态；TOP20 榜单有 20 个排名、每个有评分组成
  （rating/荣誉/淘汰赛/样本）、有评语；无空白、无错乱。

### TC-8 生涯日志
- 打开「生涯日志」。
- **通过标准**：能回看关键时刻、比赛事件、转会事件；增量同步正常；无空白。

### TC-9 个人数据 / 荣誉与生涯
- 打开「个人数据」与「荣誉与生涯」。
- **通过标准**：属性/数据展示正常（RATING 2.0、DPR、KAST、ADR 等）；荣誉/TOP20/冠军有记录；
  无越界、无 NaN/空值错乱。

### TC-10 存档往返
- 在「设置存档」：下载压缩存档 → 读取该存档。
- **通过标准**：能保存 `.json.gz`；能重新读取恢复；恢复后状态一致；无崩溃。

### TC-11 视觉与响应式核验（贯穿全部用例）
- 每个页面分别截图，核验：
  - 元素没有整体缩挤在某一角（如全部挤左上角）。
  - 没有大面积空白（内容区大量空白的页面 = 缺陷）。
  - 没有元素重叠、遮挡、文字溢出（长队名/选手名不越界）。
  - 1280px 与 390px 两种宽度下均可用（用 resize 模拟）。
- **通过标准**：全页面无上述视觉问题。

### TC-12 事件流与数值一致性（抽查）
- 抽查：选手击杀/胜场/rating 与比赛记录口径一致；TOP20 评选中 NPC 也参与同榜竞争；
  无"主角霸榜"异常。
- **通过标准**：数值自洽，无明显失真。

## 4. 自修复循环（核心协议）

### 4.1 缺陷分类
- **致命**：崩溃/白屏/无法创建游戏/无法推进/数据丢失/确定性破坏/核心流程卡死/控制台红色
  报错。→ **立即修复**。
- **非致命**：布局小错、文案不通顺、空状态缺指引、数值边界、视觉小瑕疵、个别页面空白。
  → **先记录，继续跑完当前整轮**，不打断。

### 4.2 循环流程
```
LOOP:
  1. 执行 TC-1..TC-12 一整轮（非致命问题只记录，不中断）。
  2. 收集本轮全部问题 → 分类致命/非致命。
  3. 修复：
     - 非致命：本轮结束后一并修复（高质量，带测试/类型检查）。
     - 致命：立即修复（不等整轮结束，修完从当前点继续）。
  4. 清零：
     - 停止后端/前端进程。
     - 删除构建与测试产物：`backend/target/`、`frontend/node_modules/`(如需重建)、
       `frontend/dist/`；删除测试期存档/日志/临时文件；清空浏览器 localStorage/
       sessionStorage（用 evaluate 清，或重开干净 profile）。
     - 重新 `cargo build` / `npm install && npm run build`（即"含构建数据在内的全新环境"）。
  5. 重测：从 TC-1 重新开始完整一轮（全新环境、全新浏览器、全新游戏）。
  6. 若仍有缺陷 → 回到步骤 2。
  7. 若整轮零缺陷 → 进入 §0 门禁复核。
```

### 4.3 修复质量要求
- **玩法正确**：修复必须让游戏"好玩且符合玩法"——如 LIVE 决策要有可感知反馈、Major 有压迫感、
  开放自由度真实生效。
- **架构正确**：优先扩展既有体系（DecisionPoint/LiveMatchState/DecisionRecorder/
  WorldJournal/DecisionSource/WorldEvent），不新建平行系统；不破坏确定性（种子+决策日志=同一
  世界）；规则进 `csc-simulation` 纯函数层。
- **稳健简洁**：删除狗屎代码（如 TOP20 里无调用者的 `wildcard_hit` 死代码、过时权重注释、
  旧主题 CSS 残留），但只在确认无调用者时删；删前跑回归。
- **带验证**：后端改动跑 `cargo test --workspace` + `cargo clippy -- -D warnings`；
  前端改动跑 `npm run typecheck` + `npm run build`；涉及长程逻辑跑 soak。

## 5. 图片理解 / 视觉验收协议（每页必做）

1. 每进入一个页面，先 `take_snapshot`（a11y tree）拿结构 + `take_screenshot` 拿视觉。
2. 结合两者核验：
   - **布局**：主体内容是否居中、占据合理宽度（桌面 max 1240px），没有被压到一角。
   - **空白**：内容区是否有大面积空白（若某面板应有数据却空白 = 缺陷）。
   - **重叠/溢出**：长文本是否越界、卡片是否套卡片、元素是否重叠。
   - **配色**：是否符合 HLTV 视觉（浅灰画布、白卡片、HLTV 蓝 `#2d7dd2`、涨红跌绿）。
3. 发现任何一项不符合 → 记为缺陷（视觉类），按 §4 修复与重测。
4. 若你的模型不支持读图，用**脚本化几何校验**兜底：通过 evaluate 读取各主要容器的
   `getBoundingClientRect`，断言其宽度、水平居中、不为 0 尺寸、未被压缩到角落，并把结果
   记入报告。（本环境若图片不可读，务必启用该几何校验，不可跳过视觉核验。）

## 6. 拟人化交互规范（务必遵守）

- 用**点击元素**（拿 uid）而不是 `navigate` 跳转；`navigate` 仅用于打开初始 URL 与受测页面。
- 表单用 `fill` / `fill_form` 逐字段填写，点真实提交按钮。
- 每一步之后截图，确认状态符合预期再进入下一步。
- 遇到弹窗（决策/结算/确认）用 `handle_dialog` 接受或按合理默认选择。
- 若页面渲染需要等待，用 `wait_for` 等待关键文案出现，避免竞态。
